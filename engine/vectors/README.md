# Vecteurs de test communs (v2)

`v2.json` est la référence octet pour octet du chiffrement de Shhdrop (spécification du moteur Rust, §9). Il a été produit par l'ancien moteur TypeScript (`web/src/crypto`, `web/src/transfer/link.ts`) avant sa suppression. Le moteur Rust (`cargo test`), son build WebAssembly (vitest) et les futures apps doivent redonner chaque sortie à partir des seules entrées du fichier, sans JavaScript.

## Référence figée (depuis la Task 11)

L'ancien moteur TypeScript a été supprimé (Task 11) : `v2.json` ne se régénère plus et ne change plus. Le générateur (`web/scripts/gen-vectors.ts`, lancé par `GEN_VECTORS=1 npx vitest run src/engine/vectors.test.ts`) et le test qui refaisait chaque vecteur avec l'ancien moteur restent dans l'historique git : du commit `ded5c37` (création) au commit `a693d33` (dernier commit qui les contient, juste avant leur suppression). Un changement voulu du format demandera un nouveau fichier (`v3.json`), produit par le moteur Rust et relu, jamais une modification de celui-ci.

## Conventions

- Octets en hexadécimal minuscule (`"00ff…"`). Le base64url sans bourrage n'apparaît que là où le format est lui-même du texte (liens, `k` dans `manifest_json` et `opened.manifest`, cas de `encoding`) et pour les gros blocs chiffrés (champs `b64u` des pièces, `share.tail`).
- **Règle anti-détecteur de secrets** : aucune autre chaîne base64url courte (40 à 100 caractères) qui code des octets. Le base64url d'un en-tête de 48 octets fait 64 caractères avec 10 « A » après le 11e : c'est la forme d'un jeton Dropbox, et GitHub refuse alors le push. Ces champs sont donc en hex (suffixe `_hex` dans `finalize_body`). Avant chaque commit du fichier, vérifier qu'aucune chaîne bornée ne correspond à `[A-Za-z0-9_-]{11}AAAAAAAAAA[A-Za-z0-9_-]{43}`.
- Erreur attendue : `{ "error": "<message exact>" }` à la place du résultat.
- JSON à clés triées, indentation de 2 espaces, LF final.
- **Aléa** : pour chaque cas, `crypto.getRandomValues` est remplacé par un flux SHA-256 en mode compteur (bloc i = SHA-256(UTF-8(`shhdrop/vecteurs/v2/` + étiquette) ‖ i sur 4 octets gros-boutistes)). `random` liste, dans l'ordre, les octets reçus par chaque appel : il suffit de les rejouer. Le flux n'est utile que pour régénérer.
- Entrées fixes non aléatoires : `seq` (octets 0, 1, 2, … à partir d'une valeur) ou SHA-256 d'une étiquette. Elles sont écrites en clair dans chaque cas.
- NFC des mots de passe (`argon2id`) : la version d'Unicode est celle de la crate `unicode-normalization` épinglée dans `engine/Cargo.lock` (JavaScript : celle du navigateur). Changer cette version, c'est vérifier que ces vecteurs passent toujours.
- Gros clairs : `{"xorshift32": {"seed": s, "len": n}}`. x ^= x << 13, x ^= x >>> 17, x ^= x << 5 sur 32 bits, état initial `s`. Chaque nouvel état donne 4 octets petit-boutistes, et le dernier groupe est tronqué à `n`. `plain_sha256` permet de vérifier le résultat.

## Écarts propres à JavaScript

- `shareLinkWithPassword` sur une adresse illisible (`"pas une url"`) : le vecteur garde l'erreur `Invalid URL` levée par `new URL` ; le moteur Rust rend `lien_invalide`, comme pour tout autre lien refusé.
- `parseLink("https://été.example/#…", "/")` : `new URL` convertit l'hôte non ASCII en Punycode (`https://xn--t-9fab.example`) ; le moteur Rust refuse tout hôte non ASCII (`lien_invalide`), faute des tables Unicode UTS 46. Ce refus est sans conséquence, parce que l'appelant compare toujours l'origine rendue à la sienne, qui est ASCII. Une étiquette déjà en `xn--…` est gardée telle quelle.
- `shareLink` et `manageLink` rendent un résultat ou une erreur (`Result`) en Rust, avec les mêmes messages que les vecteurs (`origine_invalide`, `base_invalide`), là où JavaScript levait une exception.
- `argon2id`, cas « passes non entières » (`ops: 2.5`) : JavaScript le refusait (`paramètres KDF invalides`) ; en Rust, `ops` et `mem` sont des `u32`, et un paramètre non entier, négatif, `NaN` ou infini ne peut pas être écrit. Le cas est sans objet ; le test vérifie seulement que le vecteur attend bien ce refus. La couche TypeScript (Task 5 et suivantes) devra refuser elle-même ces valeurs avant de les passer au moteur, avec le même message.
- `access` et `content`, refus de taille (K_lien ou K_mdp de 31 ou 33 octets, graine de 31 ou 33 octets) : en Rust, `KLien`, `KMdp` et `Seed` font 32 octets par type ; le refus a lieu à leur construction depuis des octets de taille libre (`from_slice`), avec le même message (`clé ou sel de taille invalide`, `graine invalide`). Les octets refusés sont écrits dans le cas (`fn`, `k_lien`, `k_mdp` pour `access` ; `r` pour `content`).
- `access`, K_maître et K_env : le moteur ne les rend pas (K_env n'existe que comme poignée du fournisseur). Le test vérifie la chaîne HKDF du vecteur (K_lien ‖ K_mdp → K_maître → K_env), puis que la clé rendue par `access_keys` (tenue par le fournisseur) chiffre comme K_env du vecteur importée (même sonde AES-GCM). Même méthode pour K_contenu (`content`).
- `content.probe` : l'en-tête et `nonce(0, faux)` viennent de `format::header` et `format::nonce`, eux-mêmes rejoués sur les sections `header` et `nonce`.
- `header`, refus « engagement invalide » (engagement de 31 ou 33 octets) : en Rust, `format::header` prend un `[u8; 32]` ; le cas est sans objet (le test vérifie que le vecteur attend ce refus).
- `sizing.bucketFor`, entrées `-1` et `0.5` : impossibles en `u64`, sans objet. L'entrée 2^53 est rejouée (`taille_invalide`, comme `Number.isSafeInteger`). `bucket_for` rend un `Result` (`taille_invalide`, `trop_gros`) là où JavaScript levait une exception.
- `sizing` (`segmentsFor`, `chunksFor`, `footprintFor`, `isSmall`, `reservationFor`) et `element` (`first` égal à `-1` ou `1.5`), entrées `-1` et `0.5` : impossibles en `u64`, donc sans objet. Le test vérifie que le vecteur attend bien le refus (`isSmall(0.5)` valait `true` en JavaScript). Toutes les autres entrées sont rejouées, y compris les tailles au-delà de 2^53 − 1 (`taille_invalide`).
- `sealFinal` (Rust `seal_final`) : la graine `k` d'une entrée est un `[u8; 32]` et la nature est un type (`FinalKind::Text` ou `File(nettoyage)`). Une graine de 31 octets, ou une valeur de nettoyage inconnue, ne peut donc pas être écrite (JavaScript les écrivait, et la lecture les refusait ou les ignorait). `seal_final` refuse aussi plus de 200 éléments (`MAX_ITEMS`) avec `manifeste_trop_gros`, parce que `manifest::parse` ne les relirait pas ; JavaScript ne les bornait que dans l'interface. Les droits sont passés en texte (`rights`, `keep_ttl_h`) et vérifiés par `Rights::new` (`droits_invalides`).
- `elementSealer` (Rust `ElementSealer`) ne lit pas de fichier : l'hôte lit la plage `range(j)` et la passe à `piece(j, octets)`. Une plage de mauvaise taille donne `lecture_incomplete`, comme la lecture d'un `Blob` modifié dans JavaScript.
- Lecture du manifeste (`manifest::parse`), entrées qu'aucun moteur Shhdrop n'écrit : comme `JSON.parse`, une clé répétée garde sa dernière valeur et un BOM initial est retiré (TextDecoder) ; mais une imbrication de plus de 128 niveaux, ou un nombre hors des f64 finis (`1e400`, `Infinity` pour JavaScript), sont refusés (`paquet_corrompu`) même dans un champ inconnu, là où JavaScript les acceptait.
- Demi-paire UTF-16 isolée échappée (`\ud800`, écrite par `JSON.stringify` pour un nom mal formé) : le générateur n'en met plus dans les noms (une chaîne Rust ne peut pas la porter). Le moteur Rust la lit comme U+FFFD (ce que JavaScript affichait déjà) et écrit U+FFFD ; une paire valide échappée (`\ud83d\ude00`) reste 😀. Cas construits dans `engine/core/tests/manifest.rs`.
- `splitPassword` et `shareLinkWithPassword` ne lisent que des adresses `http:` ou `https:` en Rust ; JavaScript acceptait tout schéma lisible par `new URL`. Pour un autre schéma, Rust rend le lien inchangé sans mot de passe, ou `lien_invalide`. C'est sans risque : les liens de Shhdrop sont toujours en `http(s)` (`checkOrigin` l'impose), et ce cas finit toujours par un refus.

## `share`

Il contient une note de 10 octets (`Allo été`, morceau 0), un petit fichier de 100 000 octets (morceaux 1 et 2, dans le segment 0 partagé) et un fichier de 9 Mio (segments 1 à 3 ; sa dernière pièce n'occupe que 16 des 64 morceaux du segment 3), avec les droits `enregistrer`. Le palier est 400 (7 segments). Les segments 4 et 5 ne contiennent rien, et le morceau du manifeste est le dernier du segment 6.

Les étapes tirent l'aléa dans l'ordre de `transfer/draft.ts` (`random` : `k_lien`, `s_gestion`, `k0`–`k2`, `password`, `r`, `salt`, `envelope_nonce`). Le vecteur donne aussi les dérivés (K_accès, V_accès, K_mdp, id, K_preuve, V_preuve, K_contenu, engagement), le lien, le lien de gestion, le lien du QR code, l'enveloppe E, l'en-tête, le morceau du manifeste `tail` (en entier) avec `manifest_json`, et `finalize_body`, le corps de finalisation : le serveur reçoit les mêmes octets en base64url, sous le nom sans `_hex` ; son champ `tail` est `share.tail`, dont seule l'empreinte est répétée ici.

Pièces chiffrées (`items[].pieces`) : `seg`, `from`, `chunks`, `len` et `sha256` pour chacune. Celles du segment 0 sont **en entier** (`b64u`, avec les 48 octets nuls réservés à l'en-tête quand la pièce commence au morceau 0). Celles des segments 1 à 3 (≈ 9 Mio) ne donnent que `first64` et `last64` : on les retrouve en rechiffrant le clair (xorshift32) sous `k`, puis on compare l'empreinte.

Fichier du serveur : `segments[n].size`. Pour assembler, on part de zéros, on pose chaque pièce (segment 0 : à 0 si elle commence au morceau 0, sinon à 48 + from × 65 552 ; autres segments : à from × 65 552), puis l'en-tête aux octets 0 à 47 du segment 0 et `tail` dans les 65 552 derniers octets du dernier segment. `sha256_zero_filled` est l'empreinte de chaque segment ainsi assemblé. Les morceaux non écrits sont remplis d'aléa par le vrai serveur et ne sont jamais lus. `opened` donne ce que `openStream` lit après l'ouverture complète (lien → Argon2id → enveloppe → engagement) : le manifeste et l'empreinte de chaque élément.

## Moteur WebAssembly (`web/src/engine/engine.test.ts`)

Le build WebAssembly, avec le fournisseur WebCrypto du site, rejoue les mêmes sections que `cargo test`. Les nombres y arrivent en nombres JavaScript : les cas « sans objet » en Rust (`-1`, `0.5`, `1.5`, `ops: 2.5`, engagement de 31 ou 33 octets) y sont rejoués et donnent le message de l'ancien moteur. Restent sans objet : la graine R de 31 ou 33 octets (`content`), parce que R n'entre jamais depuis JavaScript (tirée par `newSeed`, déballée par `open`), et l'hôte IDN (comme en Rust). `nonce`, `segmentCount` et `segmentSize` refusent une entrée qui n'est pas un entier sûr (`taille_invalide`) ou un segment hors du palier (`segment_invalide`), là où JavaScript rendait un nombre sans valeur ; `sealFinal` refuse une entrée mal formée ou un nettoyage inconnu (`entree_invalide`).

Depuis la Task 11, la graine `k` d'un élément ne sort plus du moteur : `elementSealer` ne la rend pas, `sealFinal` reçoit le numéro (`sealer`) du scelleur qui la tient, et le manifeste rendu par le lecteur omet `k`. Le test WebAssembly tire donc chaque `k` du vecteur par un scelleur (aléa rejoué) et vérifie la graine par la clé importée (`HKDF(k, « shhdrop/v2/element »)`) ; il compare `opened.manifest` sans ses `k`.

La partie gardée en TypeScript pour le site (`web/src/engine/pure.ts` : constantes, tailles, base64url, origine, forme des liens, mot de passe du QR code, mot de passe généré) est comparée aux vecteurs et au moteur par `web/src/engine/pure.test.ts`.

# Cas limites (`v2-limites.json`)

Supplément de `v2.json` (audit M7 du 11 novembre), **produit par le moteur Rust** et non par l'ancien moteur : `engine/core/tests/limites.rs` l'écrit (`SHH_GEN_LIMITES=1 cargo test -p shhdrop-core --test limites`), de façon déterministe, puis le relit. Sans la variable, le test échoue si le fichier n'est plus exactement celui que le moteur produit, et rejoue chaque cas à partir de ses seules entrées. `web/src/engine/limites.test.ts` rejoue les mêmes cas avec le build WebAssembly et le fournisseur WebCrypto du site, et les liens aussi avec `pure.ts` (`linkForm`, `shareLinkWithPassword`, `splitPassword`). Les apps devront le rejouer comme `v2.json`. Un changement voulu du format reste un nouveau fichier ; régénérer celui-ci n'est permis que pour ajouter des cas, après relecture du diff.

Mêmes conventions que `v2.json` (hex minuscule, JSON à clés triées, 2 espaces, LF final, `{ "error": "<message exact>" }`, règle anti-détecteur de secrets vérifiée avant commit). Aléa : flux SHA-256 en mode compteur, bloc i = SHA-256(UTF-8(`shhdrop/vecteurs/v2-limites/` + étiquette) ‖ i sur 4 octets gros-boutistes) ; les graines tirées sont écrites dans chaque cas (`k`, `r`), il suffit de les rejouer.

| Clé | Contenu |
|---|---|
| `links.written` | `shareLink` / `manageLink` (origine `https://shhdrop.example`) d'une clé dont le base64url commence par « m » (partage, aussi avec la base `/shhdrop/` ; gestion : `#mm…`), par « - » ou « _ », ou fait de 0x00 ou 0xff ; puis `parseLink` du lien écrit (`parsed` : genre, origine, clé en hex). |
| `links.parse` | `parseLink(url, "/")` : chacun des 64 caractères en 43e position, pour un partage, une gestion et un partage dont la clé commence par « m » (seuls les 16 caractères canoniques, d'indice multiple de 4, sont acceptés) ; « - » et « _ » en tête, juste avant la fin et en fin (refusé : jamais canonique) ; `#mm…` ; fragments de 42 et 44 caractères. |
| `links.qr` | `shareLinkWithPassword` d'un lien de partage dont la clé commence par « m » (mot de passe généré, avec blancs en bord, Unicode), puis `splitPassword` ; refus pour un lien de gestion. Le QR garde les blancs : c'est le calcul de K_mdp qui les retire. |
| `shares` | Partage complet : chaque élément (`kind`, `name`, `mime`, `first`, clair `plain`, graine `k`) chiffré par un scelleur, `sealFinal` sous R (`r`, droits `enregistrer`), puis ouverture complète (enveloppe, lecteur) et relecture de chaque élément. Sorties : `pieces` (par élément : `seg`, `from`, `chunks`, `len`, `sha256`), puis `bucket`, `header`, `tail_sha256`, `manifest_json` (texte exact) et `opened` (`len`, `sha256` de chaque élément relu), ou `error` au scellement. Cas : note de 100 000 points de code (acceptée) et 100 001 (`texte_trop_long`), 400 000 octets (100 000 emoji, acceptée) et 400 001 (`texte_trop_long`), note vide, BOM initial gardé, UTF-8 invalide, demi-paire UTF-16 codée, UTF-8 tronqué (`texte_invalide`) ; fichier qui finit pile à la fin du morceau B − 2 (le morceau B − 1 est celui du manifeste) pour B = 16 et B = 80, puis un octet de plus (palier suivant) ; manifeste de 200 éléments (accepté) et de 201 (`manifeste_trop_gros`). |
| `argon2id` | `passwordKey` (KDF_MIN) et `passwordKeyForCreate` : `password_utf8`, `nfc_utf8` (octets passés à Argon2id : blancs ASCII de bord retirés, puis NFC), `key` ou `error`. Les cas d'un même `same_key_as` donnent la même clé, et seulement eux : hangul composé et décomposé (jamos), Å en U+212B, U+00C5 et A + U+030A, marques combinantes dans les deux ordres (U+0301 U+0323), U+0344 (→ U+0308 U+0301) contre U+0390, emoji et séquence ZWJ ; blancs ASCII en bord (décision du propriétaire, D42-21) ; blanc intérieur et espace insécable en bord gardés (autre clé) ; rien que des blancs ou vide (`mot_de_passe_vide`) ; création avec un blanc en bord (`mot_de_passe_non_genere`). |

Notes à l'usage des apps :

- **Note (`kind: text`) au scellement** : le moteur refuse au manifeste une note que le lecteur refuserait (UTF-8 strict, au plus 100 000 points de code, `texte_invalide` / `texte_trop_long`, audit M6). Le scelleur garde le verdict du texte qu'il a chiffré (`ElementSealer::check_note`) ; une app passe par `FinalEntry::note(&scelleur, nom, type)` et `FinalEntry::file(…)`, qui prennent aussi la taille, la place et la graine du scelleur. La couche WebAssembly fait la même vérification dans `sealFinal`.
- **Mot de passe à l'ouverture** : blancs ASCII de bord (espace, tabulation, retour chariot, saut de ligne) retirés avant NFC et Argon2id (`kdf::trim_password`) ; rien d'autre n'est retiré.

# Vecteurs du salon (`salon-v3.json`)

Référence octet pour octet du moteur du salon (`engine/salon`) : clés, trames, messages, texte, pseudonymes, effacement, codes de vérification. **Produit par le moteur Rust** : `engine/salon/tests/vecteurs.rs` l'écrit (`SHH_GEN_SALON=1 cargo test -p shhdrop-salon --test vecteurs`), de façon déterministe, puis le relit. Sans la variable, le test échoue si le fichier n'est plus exactement celui que le moteur produit, et rejoue chaque cas à partir de ses seules entrées. Le site (WebAssembly) et les apps doivent le rejouer. Un changement voulu du format demande un nouveau fichier (`salon-v4.json`) ; régénérer celui-ci n'est permis que pour ajouter des cas, après relecture du diff.

**Régénéré le 13 novembre (audit adverse, second passage ; à valider par le propriétaire).** Aucun cas existant de `cles`, `trames`, `messages`, `texte`, `pseudo` ou `effacement` ne change d'un octet. Ajouts : `cles[].k_maitre` ; sorte de message `rotation` (`messages.encode` : `rotation`, `rotation_n_max` ; `messages.decode` : `rotation_*` ; `trames.coherence` : `rotation_e0_*`, 56 cas au lieu de 48). **Un changement** : `empreinte`, le code de vérification passe de 4 à 5 groupes de 5 chiffres (les quatre premiers groupes sont ceux d'avant) ; comme pour `effacement` le même jour, c'est une fonction pure d'affichage, pas un format sur le fil, d'où un remplacement ici plutôt qu'un `salon-v4.json`.

Mêmes conventions que `v2.json` (hex minuscule, JSON à clés triées, 2 espaces, LF final, `{ "error": "<message exact>" }`, règle anti-détecteur de secrets vérifiée avant commit : tout est en hex, y compris les trames, et les messages ne donnent leurs octets qu'en hex). Les entrées « dérivées » viennent de SHA-256 d'une étiquette : bloc i = SHA-256(UTF-8(`shhdrop/vecteurs/salon-v3/` + étiquette) ‖ i sur 4 octets gros-boutistes), blocs mis bout à bout ; les valeurs obtenues sont écrites dans chaque cas.

Octets décrits (`charge`, `bytes`, `in`) : `{"hex"}`, `{"utf8"}`, `{"repeat": {"unit" (hex), "n", "then" (hex, facultatif)}}` ou `{"xorshift32": {"seed", "len"}}` (comme dans `v2.json`). Les textes sont en hex UTF-8 : les invisibles et les caractères de contrôle restent lisibles. Une sortie de texte est `out_hex`, ou `out_len` et `out_sha256` quand elle dépasse 256 octets.

| `trames.coherence` | `en_tete` et `contenu` (`"controle"` pour un Commit, un Welcome ou un KeyPackage, sinon une enveloppe au format de `messages.encode`) → `ok` ou `message_invalide` (`en_tete_coherent`, ce que vérifie `recevoir_trame`) : contrôle seulement sous non volatil et désactivé ; une enveloppe sous son bit volatil (`ecrit`, `recu`, `vu`) et sa règle ; une sorte inconnue sous sa règle, bit volatil libre. |
| `messages.encode` | Enveloppe `{id, t, e, message}` (identifiants et graines en hex ; sur le fil, ils sont en base64url) → `encoded_hex` et `len`, ou erreur ; le test relit l'octet obtenu avec le décodeur et retrouve l'enveloppe. Refus : texte non nettoyé, JSON de plus de 3 900 octets (échappement des guillemets), valeurs hors bornes. Sorte `rotation` (13 novembre) : `n` (numéro de rotation, 32 bits) et `cle` (`K_maître_s'`, 32 octets, en hex ici, en base64url sur le fil). |
| `messages.decode` | Octets → `envelope` (`k: "inconnu"` pour une sorte inconnue, ignorée sans erreur) ou `message_invalide` (clé répétée, champ en trop ou manquant, version, type, UTF-8, octets après l'objet, plus de 4 093 octets…). |
| `texte` | `nettoyer_texte` : NFC, au moins un caractère visible (ni espace, ni invisible, ni marque au sens de la segmentation en graphèmes : Extend, SpacingMark, ZWJ, dont une teinte de peau seule, ni U+2800), retraits (inversions de sens U+202E…, contrôles, étiquettes sauf dans un drapeau de la liste emoji 15.0), limites de 2 000 graphèmes et 3 500 octets. |
| `pseudo` | `verifier_pseudo` et `cle_unicite` (`key_hex`) ; les cas d'un même `same_key_as` donnent la même clé, et seulement eux (ou ceux qui donnent le même pseudonyme). |
| `effacement` | `etat` : `regle`, `maintenant_ms`, `vu_par_moi_ms` (instant où cet appareil l'a vu, ou `null`), `efface_par_serveur` (`0x0E` reçu) → `visible`, `rebours` (`fin_ms`, compte à rebours local) ou `efface` ; règle 0 jamais effacée ici (fin ou renouvellement) ; règles 1 à 3 effacées seulement au `0x0E` (1 min, 5 min, 1 h après la dernière lecture : le serveur fait foi). Cas nommés (bornes à ± 1 ms, saturation) puis grille complète. Section remplacée le 13 novembre (décision du propriétaire, nouvelle règle d'effacement) : les bits du format ne changent pas, seule cette fonction pure change, d'où un remplacement dans `salon-v3.json` plutôt qu'un `salon-v4.json`. |
| `empreinte` | Clé publique Ed25519 → code de vérification (`code_verification`, 5 groupes de 5 chiffres depuis le 13 novembre ; 4 avant). |
| `role` | Ajouté le 14 novembre (rôle du créateur lié à `S_gestion`, spec salon v3 §15.2 ; à valider par le propriétaire). Entrées `s_gestion`, `tag`, `siege` → `graine_role` = HKDF(`S_gestion`, « shhdrop/v2/salon/role »), `cle_role` = clé publique Ed25519 de cette graine (RFC 8032 ; recoupée avec OpenSSL), `code` (son code de vérification), `jeton_gestion` = HKDF(`S_gestion`, « shhdrop/v2/salon/gestion-serveur ») (seul envoyé au serveur), `id_groupe` = `tag` ‖ siège ‖ `cle_role` (49 octets). Aucun autre cas du fichier ne change. |

# Vecteurs du compte v2 (`compte.json`)

Référence du compte par e-mail (conception `docs/superpowers/specs/2026-11-14-compte-email-design.md` §5.1, §6, §21.2.2, §21.5), ajoutée le 14 novembre (lot 1 du plan). Deux auteurs, chacun pour ses sections :

- **moteur Rust** (`engine/core/tests/compte.rs`, `SHH_GEN_COMPTE=1 cargo test -p shhdrop-core --test compte`) : `constants`, `normaliser`, `sel`, `deriver`, `cles`, `pseudo`, `mot_de_passe`. Les sorties attendues sont écrites à la main dans les tables du test : la génération échoue si le moteur s'en écarte ;
- **WebCrypto** (`web/scripts/gen-compte-vectors.mjs`, lancé ensuite depuis `web/` : `node scripts/gen-compte-vectors.mjs`) : `enveloppes`, `coffre_prive`, `coffre_profil`, à nonces fixés, à partir de `deriver` (KEK_mdp) et de `cles` (K_compte, s_profil). C'est le site qui chiffrera ; le test Rust refait chaque chiffré avec l'AES-256-GCM de RustCrypto (celui des apps), et `web/src/engine/compte.test.ts` les ouvre et les refait avec WebCrypto.

Sans la variable, le test Rust échoue si ses sections ne sont plus exactement celles qu'il produit ou si le fichier n'est pas sous forme canonique. `web/src/engine/compte.test.ts` rejoue toutes les sections avec le build WebAssembly, et recalcule les dérivations à part (Argon2id de `node:crypto`, HKDF de WebCrypto). Le serveur Go (lot 2) rejouera `normaliser`, les `p_canon` de `pseudo` et `constants.reserves`. Un changement voulu du format demande un nouveau fichier ; régénérer celui-ci n'est permis que pour ajouter des cas, après relecture du diff.

Mêmes conventions que `v2.json` (hex minuscule, JSON à clés triées, 2 espaces, LF final, `{ "error": "<message exact>" }`, règle anti-détecteur de secrets vérifiée avant commit). Textes d'entrée en hex UTF-8 (`entree_hex`, `mdp_hex`, `json_hex`) ; adresses normalisées et `canon` en clair (ASCII). Entrées fixes : SHA-256(UTF-8(`shhdrop/vecteurs/compte/` + étiquette)), tronqué (`k_compte/a`, `s_profil/a`, `h/a` sur 16 octets, `nonce/enveloppe/a` et `nonce/SHH-ACCT1/petit` sur 12…).

| Clé | Contenu |
|---|---|
| `constants` | Argon2id (64 Mio, 3 passes, 1 fil, 32 octets), étiquettes HKDF, bornes du mot de passe (10 à 256 points de code) et du pseudo (2 à 24 graphèmes), paliers des coffres, `reserves` (mot → `p_canon`), versions Unicode des tables (comme `salon-v3.json`). |
| `normaliser` | Adresse → `canon` et `exacte`, ou `adresse_invalide` / `adresse_non_ascii`. Règles : blancs de bord retirés (espace, tabulation, CR, LF seulement) ; un caractère non ASCII → `adresse_non_ascii` ; plus de 254 caractères, caractère hors U+0021–U+007E, pas exactement un `@` → `adresse_invalide` ; minuscules ASCII ; partie locale en « dot-atom » RFC 5322 de 1 à 64 caractères ; domaine d'au moins deux étiquettes `[a-z0-9-]` de 1 à 63 sans tiret en bord, la dernière d'au moins deux lettres ; `canon` : coupe au premier `+` (vide → refus), `googlemail.com` → `gmail.com`, points retirés pour `gmail.com`. |
| `sel` | `canon` → SHA-256(« shhdrop/v2/compte/sel » ‖ 0x00 ‖ `canon`)[0..16]. |
| `deriver` | Mot de passe, `canon` → `a_auth`, `kek_mdp` (Argon2id du mot de passe rogné puis NFC, puis HKDF), ou `mot_de_passe_vide` ; `same_key_as` : même clé que ce cas (blancs de bord, NFC). |
| `cles` | `k_compte`, `s_profil` → `k_prive` (« …/blob »), `k_appareil` (« …/appareil »), `k_profil` (« …/profil »). |
| `pseudo` | Entrée → `affiche_hex`, `p_canon_hex`, `reserve`, ou `pseudo_longueur` / `pseudo_caracteres` / `pseudo_ecritures`. Règle de `shhdrop_core::texte`, la même que le salon (`salon-v3.json`, section `pseudo`, qui ramène les trois erreurs à `pseudo_invalide`). `p_canon` passe par le squelette UTS #39 : « m » devient « rn », d'où `adrnin` pour « admin ». **Monter la version d'`unicode-security` ou d'`unicode-normalization` change des `p_canon` déjà gardés en empreinte par le serveur** : à relire contre ces cas avant toute mise à jour. |
| `mot_de_passe` | Mot de passe, adresse → `ok` ou `mdp_court`, `mdp_long`, `mdp_adresse` (en minuscules, égal à l'adresse exacte, à l'adresse canonique ou à l'une de leurs parties locales). |
| `enveloppes` | `env_mdp` = nonce (12) ‖ AES-256-GCM(`kek_mdp`, nonce, `k_compte`, AD = « SHH-CENV1 » ‖ `h` ‖ « mdp ») : 60 octets. |
| `coffre_prive`, `coffre_profil` | « SHH-ACCT1 » ou « SHH-PROF1 » (9) ‖ `gen` (8, gros-boutiste) ‖ nonce (12) ‖ AES-256-GCM(`cle`, nonce, clair, AD = magie ‖ `h` ‖ `gen`) ; clair = longueur du JSON (4, gros-boutiste) ‖ JSON ‖ zéros, **de la taille exacte du palier** (4, 16, 64 ou 256 Kio : le plus petit qui contient 4 + JSON) ; coffre = palier + 45 octets. `blob` en entier pour les cas de 4 Kio, sinon `blob_len` et `blob_sha256`. |
